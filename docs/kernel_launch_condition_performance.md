# 条件执行与队列槽位设计：评估结论和测试经验

2026-10-12。本机 OpenReg 的条件任务已改为 invocation 统一保活、逐任务借用条件指针。本次进一步将 `QueueSlot::storage` 从 256 B 调整为 **480 B**，在当前 64 位 ABI 下使整个槽位为 **512 B**。保留现有 kernel launch wrapper，条件由前序 stream 任务产生，worker 执行时判断。

本文保留设计依据、关键结果和可复用的测量方法。探索用的基准程序、历史头文件快照、隔离构建产物及逐轮 CSV 已移出仓库；本文不再引用临时脚本或结果目录。已有正式基准和功能回归测试继续保留。

## 为什么选择 storage 480 B

槽位含 8 B sequence、两个各 8 B 的函数指针，以及 storage 前的 8 B 对齐填充。实际内联上限针对完整 `TupleTask`，包含 wrapper、条件指针、event 和参数，不仅是业务捕获字段。

| storage | 整个槽位 | 16,384 个槽位的数组 | 相对旧版每 stream 增量 |
| --- | ---: | ---: | ---: |
| 256 B | 288 B | 4.5 MiB | — |
| **480 B** | **512 B** | **8 MiB** | **3.5 MiB** |
| 512 B | 544 B | 8.5 MiB | 4 MiB |

本机 `sizeof(orStream)` 分别为 4,718,976、8,388,992、8,913,280 B。修改 storage 不增加可排队的任务数量，也不放宽任务对齐限制。两个优先级各有 32 个 stream 池位置，按实际使用惰性创建；不是启动就分配全部队列。

当前 `orStream` 按 64 B 对齐，槽位数组从对象起始地址开始。512 B 步长使每个槽位从缓存行边界开始；32 B 管理区和不超过 32 B 的任务可以落在同一条缓存行内。288/544 B 步长则交替出现 0/32 B 的缓存行内偏移。

**对齐不能证明所有小任务都不退化。** 扩容仍增加页面跨度和总体内存占用，固定步长也可能改变缓存集合的使用情况。未使用的 storage 不会每次全部复制，因此不能把容量增长直接当作流量或延迟翻倍。选择 480 B 依据的是结构分析与下述对照实验的合计结果。

条件闭包在 (256, 480] B 时从堆存储转为内联；超过 480 B 仍走原有 fallback。普通直接 `orLaunchKernel` 的内联上限也增至 480 B，超过上限仍编译失败。相比 storage 512 B，480 B 少用 0.5 MiB/stream，但不覆盖 481–512 B 的任务。

## 480 B 的实测依据

三个容量使用相同源码、相同计算量、相同绑核策略，在同一轮内随机排序。以下均为 **storage 480 B 相对 256 B 的每任务耗时增量**，负值表示改善。

| 完整任务大小/组合 | 持续派发，20 轮 | 纯短任务预填，40 轮 |
| --- | ---: | ---: |
| 无条件普通小任务，24 B | −1.27 ns | −0.17 ns |
| 条件小任务，32 B | −2.35 ns | −5.22 ns |
| 条件任务，256 B | +1.16 ns | +0.90 ns |
| 条件任务，264 B | −413.64 ns | −90.02 ns |
| 条件任务，384 B | −210.20 ns | −90.73 ns |
| 条件任务，480 B | −212.83 ns | −89.16 ns |
| 条件任务，512 B，仍然溢出 | +33.25 ns | −0.37 ns |
| 1/8 为 384 B，其余为 32 B | −42.58 ns | −5.28 ns |

另起进程、更换随机顺序后复测小任务和混合序列，轮数不变：

| 任务 | 持续派发复测 | 纯短任务预填复测 |
| --- | ---: | ---: |
| 无条件普通小任务，24 B | −0.32 ns | −0.06 ns |
| 条件小任务，32 B | −3.66 ns | +0.88 ns |
| 条件任务，256 B | +1.07 ns | +2.08 ns |
| 1/8 为 384 B，其余为 32 B | −45.40 ns | −7.95 ns |

重要的统计边界：

- 普通小任务持续派发的两次 bootstrap 95% 区间分别为 −1.84～0.09、−2.13～7.68 ns，均跨零；没有测出稳定退化，也不能证明严格零开销。
- 条件小任务持续派发两次均改善，区间为 −3.08～−2.12、−4.38～−2.79 ns；但纯短任务复测慢了 0.88 ns，区间 +0.31～+1.10 ns，说明不能声称所有小任务都获益。
- 256 B 条件任务持续派发两次分别增加 1.16/1.07 ns，区间为 +0.70～+2.37、+0.40～+2.47 ns。
- 混合序列持续派发两次平均节省 42.58/45.40 ns，区间为 −44.37～−40.91、−46.52～−43.21 ns。
- 512 B 任务两种容量下都需堆存储，持续派发区间 −48.68～92.63 ns 很宽，不能把 +33.25 ns 的点估计当作稳定惩罚。

三种容量的同期比较中，480 B storage 在这些小任务和混合序列上的点估计均优于 512 B storage。更早单独比较 storage 256/512 B 时，264–512 B 任务持续派发约节省 207–385 ns，普通小任务没有稳定差异，256 B 任务则增加约 6–10 ns。这些历史数据不是本次三方实验的直接差值，不能混合相减。

**选择结论：采用 480 B storage，兼顾较大任务内联与规整的槽位布局，接受每 stream 多 3.5 MiB 的代价。** 本结论来自单队列模拟推理序列；尚未测量真实模型闭包尺寸分布、多流缓存争用和端到端吞吐，不能推广为所有部署下的固定收益。

## 条件执行和 shared_ptr 的经验

原来的条件 launch 为每个任务捕获 `shared_ptr`。host 提交时增加引用，worker 执行后析构任务、减少引用，再执行下一个任务。因此，即使 host 派发很快，worker 的原子引用释放仍落在串行执行间隙中。两核写同一个控制块还可能产生缓存行所有权转移。

复制已有 `shared_ptr` 不会每次分配控制块。历史上约 340 ns 的大闭包开销包含超限后的堆分配、间接访问和释放，不能称为“一次 shared_ptr 原子操作的耗时”。在本机 ABI 下，shared_ptr 本身占 16 B，增加捕获可能使原本内联的任务跨过阈值。

使用一次 invocation 保活、每个条件任务仅借用 `const bool*` 后，保留原有 wrapper 即可避免逐任务引用计数。单纯把 if 移进 kernel，但继续额外捕获 shared_ptr，不能解决该成本。生命周期 API 和异常路径契约见 [迁移指南](kernel_launch_migration.md#stream-produced-launch-conditions)。

以下是 storage 256 B、持续派发且条件恒成立的小闭包实验，不应当作扩容后的新测量：

| 路径 | 相对无条件旧版增量 | bootstrap 95% 区间 |
| --- | ---: | ---: |
| 新版，不启用条件 | +0.04 ns/任务 | −0.28～0.54 |
| 旧条件实现，逐任务 shared_ptr | +39.69 ns/任务 | 38.90～42.10 |
| 新版，scope 保活兼容 API | +0.05 ns/任务 | −0.35～0.57 |
| 新版，invocation 保活 | +0.28 ns/任务 | −0.26～0.90 |
| kernel 内直接判断、无逐任务所有者 | −0.12 ns/任务 | −0.40～0.35 |

32,768 个任务的总时间中位数：无条件旧版 107.100 ms，旧条件实现 108.433 ms，新 invocation 实现 107.108 ms。各自总时间中位数相减不等于配对差值中位数；亚纳秒结果应解释为未测出稳定差别，而非精确成本。早期 sleep 预填交叉检查的小闭包增量约 31.51 ns，与旧 shared_ptr 路径固定计算量预填结果接近。

## 可复用的性能测量方法

### 先确定测量问题

目标是 host 派发快于 worker 执行、队列持续有任务时，新增功能对执行序列的影响。不要用 host enqueue 吞吐或逐个 launch 后同步的计时替代这个问题。

采用固定工作量，只在 worker 的序列首尾计时：

```text
每任务等效间隙增量 = (候选序列 worker 总耗时 − 基线序列 worker 总耗时) / 任务数
```

它包含条件判断、任务析构、槽位回收、队列和内存访问成本，是等效增量，不是直接逐 kernel 测量的空闲间隔。避免逐任务时间戳扰动被测路径。

### 构造相同工作量并证明供给充足

- 主场景：32,768 个任务，先预填 8,192 个再放行 worker，host 继续提交。总任务数超过 16,384 个槽位，覆盖队列复用。
- 每 64 个任务一个慢任务，执行 100,000 次 xorshift 循环；其余执行 8 次。公共计算 body 不内联，不因 wrapper 不同而替换算法，输出使用可观察的累积值。
- 纯短任务：先填满整段 8,192 个任务，再开始执行，全部执行 8 次循环。计时期间没有 host 派发，帮助暴露间隙成本。
- 初始阻塞任务在 stream 上产生 true 条件。条件由 worker 读取，host 不读回；包含保活尾任务的成本。
- 每种实现、容量、任务大小必须得到相同最终结果，防止跳过工作被误认为提速。
- 单独构建供给校验版本：在每个 kernel 入口读取下一槽位 sequence，确认下一任务已经发布。只检查 tail 大于 head 只能证明已预留，不能证明任务构造完成。正式性能版本不含该检查。
- sleep 可作交叉检查，不作为唯一依据；实际睡眠包含调度和唤醒延迟，不等于请求时长。

### 控制 ABI、拓扑与实验顺序

- 本机 Intel Xeon Platinum 8592+，GCC 13.3.0，`-O3 -DNDEBUG -std=c++17`。内存保护、同步 launch、profiler 均关闭。
- host CPU 30、worker CPU 32，同 NUMA 的不同物理核；先绑 host 再分配队列。CPU 30/31 实际跨 NUMA，不能凭连续编号判断拓扑。其他机器先核对 `lscpu -e=CPU,CORE,SOCKET,NODE`。
- 容量对照必须同时重编 worker 与提交端。实验使用隔离头文件副本和真实 OpenReg worker 源码，动态库符号隔离，避免两种 `orStream` 布局混用。
- 槽位实验使用真实 `queue_conditional_task` 和等价的 timed 条件闭包；省略 host TLS 查找、关闭状态下的 profiler 预留。其绝对时间不能与完整 launch 实验直接相减。
- 槽位实验每次创建一个 stream，先完整预热一次再测量；同时只保留一个 worker，避免多个 busy worker 抢同一绑核。创建和销毁 stream 不在计时区间内。
- 配置按轮随机排序，丢弃前 3 轮，再取 20 或 40 轮。480 B 主实验 seed 781，另进程复测 seed 1811；早期完整 launch 实验使用 8 轮预热、40 轮正式测量。
- 所有正式性能实验串行执行，不与编译、MPI 或其他性能测试并行。

### 正确解释统计和异常结果

先计算同一轮候选与基线的差值，再对差值取中位数；同时报告 bootstrap 95% 区间。槽位实验重采样 4,000 次，早期 launch 实验 2,000 次。不要拿两组独立中位数相减冒充配对统计。

不同进程应保留为独立复测，不能为了缩窄区间而简单合并。两次 480 B 纯短任务实验的普通小任务基线中位数为 17.47/54.50 ns，说明绝对时间对运行状态敏感。频率未锁定，未采集缓存、TLB 或分配器事件计数；统计区间也不能覆盖所有系统性误差。

应同时覆盖普通小任务、条件小任务、旧阈值边界、新阈值边界、两版都溢出的控制组，以及稀疏大任务的混合序列。对仍然溢出的任务出现的差值，不能解释为“省掉了堆分配”；也不能只用全大任务实验线性推算真实混合序列。

## 功能验证与后续维护

性能与功能分别验证。此前 invocation 生命周期修改在 storage 256 B 下完成：MCPU launch/stream/vLLM launch/profiler 108 passed、3 skipped；EP 绑定 28 passed；4-rank MPI 的 V5/V6 × topk 6/8 × BF16/FP32，分块 eager、新缓存 torch.compile、不分块 eager 均通过。分块覆盖空输入、dummy、提交 6 轮但实际只执行 1 轮等情况；worker 阻塞 2 秒时 host 仍能异步提交。

正式回归应保留：条件 true/false、跳过任务仍析构捕获、嵌套和跨 stream 拒绝、提交中途失败、状态恰好释放一次、切换 current stream 后仍在原 stream 清理。溢出测试应根据 `sizeof(QueueSlot::storage)` 构造边界，不能固定旧的填充数组长度，否则扩容后会悄悄丢失覆盖。

480 B 源码落地后的提交准备阶段，隔离构建的 OpenReg 完整测试通过 53 项，另有 1 项原有 disabled 测试；满尺寸 480 B 任务连续入队 32,768 次、跨越队列复用后结果正确，并以编译期断言核对 storage 480 B、slot 512 B、storage 偏移 32 B 和 stream 对齐 64 B。当时仅做隔离检查；后续最终审查完成了依赖重建与集成验证，见下节。

**ABI 注意事项：** storage 480 B 改变槽位步长及 stream 的 head/tail 等字段偏移。部署时必须同步重建 OpenReg、torch_mcpu、torch_xcpu、mpi_ext 和所有包含入队模板的扩展，并重新生成旧 JIT/Inductor/AOT 产物；不能只替换其中一侧。历史功能结果不能冒充新 ABI 全套集成验证。

## 最终审查：profiler、同步、多流与优先级

2026-10-12，在 480 B 独立提交 `0cb2471` 后审查完整工作区。发现并修复三项问题，其中后两项是原有运行时问题，不是条件执行或 480 B 改动首次引入。

| 项目 | 发现与修复 | 验证 |
| --- | --- | --- |
| 同步 launch 调试模式 | 新的保活尾任务绕过普通 wrapper，没有遵循同步 launch 开关；现在同步模式等待原 stream 的尾任务，并在等待时按需释放 GIL，异步正常路径仍直接返回 | 单独以同步宏编译真实 launch 实现，检查阻塞任务后的 scope 返回时 stream 已完成，以及条件 true/false |
| 多 host 线程 profiler | 原全局 count 非原子递增，多线程可预留同一个事件槽；改为有上限的原子 CAS 预留 | 修复前 8 线程预期 160,000 次预留，仅记录约 17,011–22,696 个；修复后三轮均为 160,000 个记录和唯一槽位 |
| block/hybrid worker 唤醒 | 原 notify 不持有 wake_mutex，可落在 worker 检查条件与真正进入 wait 的间隙，丢失唤醒；现在通知与等待使用同一 mutex 协调 | 修复前第 3 次提交即复现已发布任务停顿，额外 notify 后恢复；修复后 100,000 次唤醒完成，加入正式 10,000 次循环回归 |

默认 busy worker 不进入新增锁路径；profiler 关闭时也不进入新增槽位 CAS。此前性能结论对应的默认 busy、关闭 profiler、异步 launch 路径没有因此新增逐任务锁或引用计数。

新增正式并发回归：4 个 host 线程、4 条 stream，两个优先级分别有 true/false 条件；每线程 2,048 个 timed kernel。检查 8,192 个事件预留、4,096 个实际执行、4 个独立 stream ID，以及 4 个 invocation 状态均释放。它同时覆盖条件 TLS 隔离、profiler 并发预留、低优先级唤醒和尾任务生命周期。

同步与 profiler 的保留语义：

- 条件为 false 仍消费队列项、析构捕获并推进 completed；因此后续 event/stream 等待能够越过被跳过的任务。
- `record_event`/`wait_event` 使用底层队列，不会被条件 scope 自动跳过；跨流条件 launch 则显式拒绝。使用独立条件状态的不同 stream 可以并发。
- 保活尾任务无条件执行，使用创建时捕获的 stream；正常异步路径不新增 stream/device synchronize。异常入队失败才回退到原 stream 同步，同步 launch 调试模式按开关等待。
- profiler 跳过零时间戳事件，保活尾任务不生成伪 kernel 时间；跳过任务仍消耗预留槽，整体上限仍为 262,144。reset/snapshot 需要先停止提交并同步，原子预留不等于可与活跃 worker 并发读取/清空。
- profiler 启停原有 device synchronize 和 MPI window cleanup 的原有 device synchronize 保留；不能把这些既有生命周期操作误认为正常 kernel 序列中新引入的同步。
- 本后端 priority 主要选择 busy/block 等 idle policy，没有实现高优先级 kernel 抢占或跨流执行顺序保证。

**仍保留的 EP 多流限制：** V5/V6 的 MPI window context 是进程级全局对象，`MpiWindowContext` 本身明确要求串行访问；V5 还有共享计数数组。Invocation state 独立不代表 window、通信缓冲区和 collective 顺序也独立。多个 EP 调用必须在同一通信 stream 上顺序执行，或用 event 依赖把整个 dispatch/compute/combine/reduce 序列排序，并保证各 rank 的 collective 顺序一致。真正重叠执行需要分别设计 window、通信上下文和 MPI 线程级别支持，本次没有声称支持或用局部互斥锁掩盖该问题。

最终验证使用 480 B ABI，已重建并安装 torch_mcpu、torch_xcpu、mpi_ext：

- MCPU launch/stream/vLLM launch/profiler 加 EP 绑定：137 passed、3 skipped、14 subtests passed。
- OpenReg：54 passed，1 项原有 disabled 测试。
- 4-rank MPI：V5/V6 × topk 6/8 × BF16/FP32，分块 eager、新缓存 torch.compile、不分块 eager 全部通过；eager 异步检查与实际轮数检查通过。
- 同步 launch 定向检查和 100,000 次低优先级唤醒检查通过。

常规构建仍为内存保护 OFF、同步 launch OFF；同步模式使用定向编译检查，并非整个测试套件在同步构建下重跑。以上测试验证通用多流与单通信流 EP，不覆盖不受支持的重叠 EP 多流。
